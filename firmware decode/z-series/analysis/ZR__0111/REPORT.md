# ZR__0111.bin 容器逆向：第一轮

分析日期：2026-10-04 至 2026-10-05。对象为本地样本；没有执行固件、生成刷写补丁或访问相机。

## 当前结论

**ZR 1.11 尚未解包。它不能像本地 Z6/Z8 样本那样，仅调整起点就使用已知三表 XOR 解出目录。**
本次完成包头结构定位、旧算法全相位排查、重复模式统计，并从 Z8 的明文代码还原了旧包前缀的 SHA-1 校验。

已确认的 ZR 结构：

- 原文件唯一一处连续 32 字节空格位于 `0x260`，而 Z6/Z8 为 `0x20`。
- `0x220–0x23F` 与 `0x00–0x1F` **逐字节逆序相同**。
- `0x120–0x21F` 按小端 u16 解释有 128 个不同值，全部小于 `0x8000`。
- 若把 `0x280` 当作旧目录头的位置，对旧三表算法全部 `2^24` 个相位检查，**零个相位**能恢复旧目录中的两个零保留字段。
- 从 `0x260` 对齐统计的 457,653 个完整 256 字节块，在消去每块的单字节 XOR 常量后仍全部不同。

以上足以否定“只需把旧工具的跳过长度改成 `0x260`”这一方案，但**不能据此确认 AES、RSA、密钥长度或具体加密模式**。
尚未取得 ZR 分段名称、CRC、处理器入口或文件系统；不能把 Z8 的 AArch64/Linux 分析结果直接算作 ZR 的实测结果。

## 包头分区

这些边界按观察到的排列标记，尚不是已还原的格式定义。

| 原文件区间（尾端不含） | 长度 | 观察与限制 |
| --- | ---: | --- |
| `0x000–0x020` | 32 | 非明文前缀；语义未知 |
| `0x020–0x120` | 256 | 未解释字节区；不能仅凭长度称为 RSA 签名 |
| `0x120–0x220` | 256 | 128 个小端 15 位数值；最小 153，最大 32757 |
| `0x220–0x240` | 32 | 首 32 字节的逆序副本 |
| `0x240–0x260` | 32 | 另一未解释字节区；未证明是密钥、IV 或摘要 |
| `0x260–0x280` | 32 | 全部为 `0x20`，与旧容器的空格标记相同 |
| `0x280–EOF` | 117,159,344 | 高熵主体，尚未得到有效目录 |

首 32 字节：

```text
420601f57f69308eab4d2a4ea3f486e256d93c6d8f165c968e99e4d20a029fb3
```

`0x220` 的副本：

```text
b39f020ad2e4998e965c168f6d3cd956e286f4a34e2a4dab8e30697ff5010642
```

128 个 u16 的奇偶分布为 66 偶、62 奇；其全部低于 `0x8000` 是结构性线索。
一次性探测了连续 MSVC `rand()`（`214013*s+2531011`）与常见 ANSI LCG（`1103515245*s+12345`）
的 `(state>>16)&0x7fff` 输出模型，均无法匹配完整序列。
这只排除这两种**直接连续输出**模型，不排除抽样、重排、其他 PRNG 或非随机字段。

## 旧 XOR 排查的依据

旧工具在原文件 `0x00/0x20` 找不到空格标记，按设计拒绝解析。
把 `0x260` 后内容单独按旧容器解释，也会在目录项数检查处失败。
以候选起点 `0x260` 解出的 16 字节目录头为：

```text
b13ea8e9b0efcba249b506772ae3ca88
```

这不是合理的旧格式 `count, header_size, reserved_0, reserved_1`。

为避免遗漏纯粹的 XOR 索引错位，脚本对候选目录头 `0x280–0x28F` 覆盖全部 `16,777,216` 个相位。
使用旧格式后 8 字节应为零的条件先筛选，再检查大端目录数量和长度；**第一步就没有候选**。
算法保留 64 KiB 跨界进位和 16 MiB 回绕，测试覆盖这两个边界。
用同一算法检查 Z8 则能找到已知相位 `0x20`；短目录头有等价相位，最终解包仍需完整 CRC 验证。

该结论限定于“当前位置是旧格式目录头且使用已知三表”的假设。
它不排除新目录布局、替换 XOR 表、额外变换或嵌套加密层。

另将每个 256 字节块归一化为 `block[i] XOR block[0]`，消除块级常量掩码后统计：

| 样本 | 块起点 | 完整块数 | 不同归一化块数 | 最大重复次数 |
| --- | --- | ---: | ---: | ---: |
| ZR 1.11 | `0x260` | 457,653 | 457,653 | 1 |
| Z8 3.11 | `0x20` | 386,918 | 332,889 | 44,541 |

ZR 在此检验下没有 Z8 常见的重复模式。内容差异也会影响统计，不能把这一项当作密码算法鉴定。
原始 ZR 全文件未命中 `ELF`、`NISI` 或 FDT 魔数。gzip 三字节魔数有 8 个命中，
脚本另外尝试有限解压以区分随机命中，结果保存在清单的 `gzip_probes`。

一次性尝试从头部 16 字节对齐窗口直接取 AES 密钥/IV，测试 CBC/ECB 首块及旧 XOR 叠加，未恢复合法旧目录。
这是有限候选测试，不能排除经过派生、查表或封装的密钥；后续应从实际读取代码取得算法，而不是继续无依据枚举。

## Z8 参照代码的新发现

为追踪 ZR 的新增包头，本轮检查了现有 Z8 EG 中的 `FirmwareManagement` 和 `FirmwareChkLib`。
**本节代码均来自 Z8 3.11，不是 ZR 解密产物。**

### 固件内的旧三表解码器

在 Z8 EG 文件偏移 `0x00EC49F4`（地址 `0x410249F4`）找到三表 XOR 循环。
它以完整容器起点调用时跳过最初 32 字节，使用低/中/高 8 位索引三张表，吻合现有解包工具。
固件内的表位于 EG `0x03F63CB0`，与仓库旧表不是直接逐字节相同，而分别相差固定 XOR 常量：

```text
table A: 0x40
table B: 0xCB
table C: 0x8B
0x40 XOR 0xCB XOR 0x8B = 0
```

因此三张表组合后的密钥流完全相同。这也解释了为什么直接搜索原始表的 256 字节连续数据没有命中。

### 外层前 20 字节已解释

Z8 更新检查调用者位于 EG `0x00EC7730`（地址 `0x41027730`），其流程包含：

1. 跳过外层 32 字节，在其后调用三表 XOR 解码器。
2. 将原包前 20 字节设置为待比较摘要。
3. 设置常量 `0x451` 和字符串 `Z_8`，派生 8 字节数据。
4. 计算解码容器（包括尾部）与这 8 字节拼接后的 SHA-1，进行 20 字节比较。
5. 成功后继续进行 CRC 检查等处理。

校验用种子位于 EG `0x04A2A3F0`：`138c3f279ade6b59`。
查表变换函数位于 `0x01032BDC`；状态初始化、摘要生成及比较位于 `0x01032DE4–0x010330E0`。
SHA-1 块更新函数还可从 `0x010330E4`、压缩函数 `0x010331F4` 继续跟踪。
参数 `0x451` 的业务含义未确认，不能将它叫作固件版本号。

逐条翻译调用参数与变换，所得尾部为 `6c12037e6fcec19a`，使用 Python 标准库独立计算：

```python
sha1(decoded_package + bytes.fromhex("6c12037e6fcec19a")).hexdigest()
# 61060072cc6f4032491ef95570e1e7e9e053b8fd
```

结果与 Z8 原文件 `0x00–0x13` **完全相同**。
`0x14–0x1F` 的另外 12 字节仍未解释；该路径也不是对真机完整认证链的证明。
本次未验证 Z6 是否使用相同参数或尾部。

对 ZR 不能照搬此公式。额外尝试了在原文件 `0x20/0x120/0x220/0x240/0x260/0x280` 各处开始取数据，
枚举同一 Z8 种子和两字节状态参数产生的 65,536 个候选尾部，均未匹配 ZR 前 20 字节。
这些只测试了原始后缀，没有 ZR 明文，不能排除解密后仍使用类似摘要。

## 复现与产物

从仓库根目录运行：

```sh
cd "firmware decode/z-series"
python3 tools/analyze_zr.py ZR__0111.bin --output analysis/ZR__0111 \
  --z8-firmware Z_8_0311.bin --z8-directory analysis/Z_8_0311
python3 -m unittest discover -s tools -p 'test_*.py'
```

不需要 Z8 参照检查时可省略两个 `--z8-*` 参数。
脚本以 SHA-256 限定本次样本；Z8 的固定偏移使用前还会核对原包、EG 和解码容器三个指纹。
Python 标准库即可完成核心检查；安装 `capstone` 时生成代码摘录。

- [manifest.json](manifest.json)：ZR 原始观察、全相位探测、统计与 Z8 校验结果。
- [code_landmarks.asm](code_landmarks.asm)：明确标注为 Z8 的参照代码及地址。
- `header.hex.txt`：ZR 原始前 `0x300` 字节，生成文件由 Git 忽略。
- `entropy.csv`：ZR 每 64 KiB 的熵数据，生成文件由 Git 忽略。
- [analyze_zr.py](../../tools/analyze_zr.py)：可复现的分析脚本，**不提供 ZR 解密功能**。

原固件未修改。现有测试和新增测试共 **18 项通过**，覆盖全相位搜索的跨界条件、
非法目录判定、块归一化，以及旧前缀校验对容器头/尾和派生尾部损坏的拒绝。

## 下一轮最有价值的工作

1. 取得另一份官方 ZR 版本，对比 `0x20–0x260` 的字段是否固定、长度是否稳定，以及反序副本是否仍存在。
2. 优先寻找采用相同新前缀格式的机型或较早版本中可读的更新程序，定位 128 个 15 位值与 `0x240` 区域的实际使用方式。
3. 若更新程序不能从文件中取得，再考虑已有的合法机内转储；从包读取、解封装到旧目录解析的调用链恢复算法。

当前具体缺口是 **ZR 新包头的读取/变换代码或能约束它的第二份样本**，不是旧 XOR 表或旧 CRC 参数。
本轮没有找到足以确定 ZR 解密算法的公开技术资料，也没有将旧照片签名或其他机型的密码实现当作 ZR 固件证据。
