# Z8 3.11：传感器参数装载与采集尺寸转换

本轮确认了资源 `0x5c` 的 RAM 目的地址及复制参数，并连接了采集上下文中的有效尺寸到传感器后端模式选择的主要转换。**参数块的实际字节仍未取得，尚未证明全高视频读出，也未生成 Open Gate 补丁。**

关键新增约束：在所测视频请求分支中，越界尺寸值虽然能经过此前的采集快照更新，却会在服务适配层转换为子模式 0，随后选中后端模式 0。仅放宽 SDK 白名单或传递新尺寸枚举，不能据此认定会产生新的读出窗口。

输入仍为 Z8 3.11 的 `eg2070_0311b0.bi`，SHA-256 为 `f85e0138e2f5e660ece8560de62e0d12cb795e0e14983e50f20b61dce906c46c`。产物：[复现工具](../../tools/reverse_z8_sensor_inputs.py)、[清单](manifest.json)、[原始指令摘录](code_landmarks.asm)。完整探针结果 `probes.json` 在本地生成。

## 1. 资源装载：已确认复制地址，尚缺内容

前一轮[传感器后端调查](../z8_sensor_backend/REPORT.md)定位资源 `0x5c` 的长度为 `0xf2000`，分组 38 的基址为 `0x47e80000`。本轮继续执行资源初始化函数 `0x40d70dbc` 的前缀，确认它为该资源描述符的备用指针字段赋值 **`0xa155d78c0`**。

后续装载路径为：

```text
40d6bff4(0x5c)
  → 40d6c320（整理装载描述符）
  → 40d702bc → 40d70370（检查分组尾标）
  → 40ca95fc(destination, source, length)
```

复制调用的三个实际参数：

| 参数 | 值 |
| --- | --- |
| 目的 RAM 地址 | `0xa155d78c0` |
| 来源地址 | `0x47e80000` |
| 长度 | `0xf2000`，即 991,232 字节 |

分组预留跨度为 `0x100000`，尾标检查地址由 `0x40d70b4c` 算出，为 **`0x47f7fffc`**。这与有效内容末尾 `0x47f72000` 不同，不能用有效内容长度直接定位尾标。检查代码要求四字节 `ENDM`。

验证分为两个明确阶段：

1. 不映射来源区，原始装载函数在 `PC=0x40d70468` 读取 `0x47f7fffc` 时产生预期的未映射访问。
2. 仅映射尾标所在页，写入**合成** `ENDM`，并拦截复制函数使其返回零。原始装载函数此时返回 1；之后资源查询 `0x40d6b4f4(0x5c)` 返回已赋值的 RAM 地址。

这证明装载参数和成功状态下的指针切换，不代表真实资源校验或复制成功。实验没有映射实际参数载荷及目的 RAM，没有读取或复制任何参数字节。尚不能判定来源地址对应固件内嵌数据、其他存储映射或机身专有数据。

## 2. 有效尺寸到后端请求的转换

实际采集上下文的有效尺寸位于 `+0x38c`，来源为 DataID `0x0400211e`；此前的[采集状态调查](../z8_capture_state/REPORT.md)已验证其上游更新。本轮进一步找到实际上下文构造函数 `0x40f28488`，由 `0x40f79348 → 0x40ec78cc` 调用。

**设置快照与实际采集上下文是两种结构。** 尺寸字段恰好都在 `+0x38c`，但相邻偏移不能沿用同一解释。实际构造函数先读取 DataID 列表，再经过缓存字段重排构造上下文：

| DataID | 设置快照偏移 | 构造缓存偏移 | 实际采集上下文偏移 |
| --- | --- | --- | --- |
| `0x0400211e`，有效尺寸 | `+0x38c` | `+0x168` | `+0x38c` |
| `0x04002120` | `+0x39c` | `+0x16c` | `+0x390` |
| `0x2171`，帧率枚举 | `+0x3a0` | `+0x170` | `+0x394` |
| `0x0400211b` | 此处不展开 | `+0x174` | `+0x398` |
| `0x2124` | `+0x3b4` | `+0x180` | `+0x388` |
| `0x2869` | 此处不展开 | `+0x3f8` | `+0x3a0` |

列表 `0xa02a4c360` 包含 11 项，顺序为 `218c, 2124, 2167, 0400211e, 04002120, 2171, 0400211b, 2312, 2869, 286a, 286b`。构造函数调用事务读取器 `0x40f23658` 取得这些值；`0x40f28590…0x40f28620` 将其重排到缓存；`0x40f2888c…0x40f288f4` 和 `0x40f28960…0x40f28980` 再写入上述上下文字段。

新的调用和字段关系如下：

```text
DataID 0x0400211e
  → 40f28488 的缓存及字段重排 → 采集上下文 ctx+0x38c
采集上下文 ctx
  ├─ 40f88a78 → 40f889a8 → 410666f8 → ctx+8（派生选择值）
  └─ 40f81cc4 → 41034fa4
       → 41031da0：ctx+0x38c → source+0x3c
       → 40f4e108 → 40f5bfd8
       → 40f5c18c…40f5c22c：source → request
       → 41158850：request → 411717f4 → working_config+0
```

大函数之间的调用点通过静态指令连接；隔离仿真执行的是下面列明的函数或有边界的片段，由测试工具传递结构内容。**没有执行完整采集状态机或整次配置事务。**

`0x41031da0` 前缀把 `ctx+0x38c` 原样写入 `source+0x3c`。服务层随后用六项表 `0xa029d8ed0` 转换它：

| 有效尺寸枚举 | 写入请求 `+0x1c` 的子模式 |
| --- | --- |
| 1 | 1 |
| 2 | 2 |
| 3 | 3 |
| 4 | 2 |
| 5 | 2 |
| 6 | 3 |
| 0 或大于 6 | 0 |

因此尺寸枚举并非直接成为后端模式编号。另一条路径根据上下文生成请求的 `+0` 和 `+4` 字段；后端选择函数组合这些字段与上述子模式，才生成工作配置的模式值。

具体而言，在 `ctx+0=1` 且本实验其他控制状态置零时，`0x41035d98` 生成的值经表 `0xa029da170` 转换后，请求 `+0=5`。这一分支的子模式 0 在 `0x411717f4` 中返回后端模式 0。**后端模式 0 本身也是有效模式，不能把它描述为显式拒绝。**

仿真组合覆盖：DataID `0x2869` 值 0…6、`0x2124` 值 0…8、`0x04002120` 值 0／6，以及尺寸值 0…7／`0x7fffffff`，共 **1,134 组**。帧率枚举固定为 6；DataID `0x218c=1` 经原始代码生成 `ctx+0=1`。尺寸 0、7、`0x7fffffff` 在这些组合中均产生子模式 0 和后端模式 0。

上述穷举取值是合成输入，不能称为真机可用的 FX／DX、N-RAW 或其他格式配置。清单中的 `example_baseline` 也不代表相机允许的组合。设置快照 `+0x388` 的 `0x2835`、`+0x390` 的 `0x04001dc8` 不能用于命名实际采集上下文中的相同偏移。

进一步执行真实派生回调后，已确认下面的格式及帧率转换；`0x2124` 各编号的完整业务含义仍不在本轮结论内。

## 3. 从原始 SDK 模式生成后端模式

为避免直接猜测派生字段，本轮增加 80 个 SDK 原始模式的组合实验：执行真实 SDK setter，将其设置输出填入设置快照，再依次执行以下注册回调：

| 注册节点 | 回调 | 本实验关注的结果 |
| --- | --- | --- |
| `0x06001206` | `0x40f1ae50` | 有效文件类型 `0x2312`，格式族 `0x2869` 等 |
| `0x0400211e` | `0x40ee0070` | 有效尺寸 |
| `0x04002120` | `0x40ee02bc` | 后端帧率选择值与输出帧率 `0x2171` |
| `0x07001201` | `0x40ee1924` | 采集区域选择值 `0x2124`、`0x219f` |

每次回调产生的更新由工具明确提交到快照，再读取生成的属性，经过上一节的真实构造片段和后端选择函数。基线为设置快照 `0x280c=1`、`0x218c=1`、内部状态快照 `+4=1`；其他状态及全局量置零。**回调顺序由工具安排，事务调度和完整上下文构造仍未执行。** 80 项验证证明这个基线下的代码数据流，不是对相机全部实际状态的验证。

文件类型原始编号与 `0x2869` 并不相同：

| SDK 分支使用的内部文件类型 | `0x2869`／实际上下文 `+0x3a0` |
| --- | --- |
| H.264 MP4：1 | 0 |
| H.265 8-bit：2 | 1 |
| H.265 10-bit：3 | 1 |
| ProRes 422 HQ：4 | 2 |
| ProRes RAW：5 | 3 |
| N-RAW：6 | 4 |

其中 19 个 N-RAW 原始模式的结果如下。此表记录的是上述明确基线下的选择结果，尚未执行参数解析或硬件应用。

| N-RAW 尺寸 | SDK 帧率标签 | `0x2124` | 派生选择值 `ctx+8` | 后端模式 |
| --- | --- | --- | --- | --- |
| 8256×4644 | 60、50、30、25、24 | 4 | 4 | 7 |
| 5392×3032 | 60、50、30、25、24 | 5 | 5 | 13 |
| 4128×2322 | 120、100、60、50 | 4 | 8 | 15 |
| 4128×2322 | 30、25、24 | 4 | 4 | 9 |
| 3840×2160 | 120、100 | 7 | 6 | 16 |

这首次将原始 N-RAW 尺寸／帧率设置、派生属性、实际上下文字段与此前后端模式表连接起来。不能把表中的后端编号直接当成分辨率枚举，也不能把这些已有模式当成全高模式。

帧率还存在两层：`0x04002120 → ctx+0x390` 与 `0x2171 → ctx+0x394` 在普通模式下相同，但在三个 H.264 慢动作条目中不同。输出帧率标签 30／25／24 对应的前者为枚举 0／1／0，即 120／100／120 标签；后者仍为 30／25／24。这与慢动作采集和输出帧率分开表示的解释一致，物理时钟仍未验证。

## 4. 修正帧率字段的解释

前一轮报告曾将 DataID `0x2171`／**设置快照** `+0x3a0` 标成视频文件类型。**该字段实际是有效帧率枚举，原报告与代码摘录标签已修正。** 实际采集上下文中的对应偏移是 `+0x394`。

证据相互对应：

- 快照更新分支 `0x40f3f3e0…0x40f3f404` 读取 `0x2171` 并存入设置快照 `+0x3a0`。
- SDK 读取函数 `0x40841bfc` 依次读取有效尺寸 `0x0400211e`、`0x2171` 和 `0x2170`，将它们传给打包函数 `0x40811da4`。
- 打包函数通过表 `0x440f0398` 把第二参数转为帧率标签，并写入打包结果的第 16…23 位。

| 内部枚举 | SDK 帧率标签 |
| --- | --- |
| 0 | 120 |
| 1 | 100 |
| 2 | 60 |
| 3 | 50 |
| 4 | 30 |
| 5 | 25 |
| 6 | 24 |

7 项均通过原始快照更新函数与原始打包函数验证。此处是 SDK 的整数标签，不据此断言时钟的精确有理数帧率。先前 SDK setter 对文件类型 `0x06001206`、RAW 尺寸／帧率 DataID 的分析不受这一字段修正影响。

## 5. 复现与边界

```sh
cd "firmware decode/z-series"
python3 tools/reverse_z8_sensor_inputs.py
python3 tools/reverse_z8_capture_state.py
```

需要 Capstone 和 Unicorn。工具先核验固件 SHA-256，再执行有指令预算的探针；分析通过后才生成输出。

帧率身份探针执行真实快照更新和 SDK 打包函数。采集链探针执行真实 DataID 批量读取、构造缓存与上下文字段重排、选择值生成、请求字段适配、后端模式选择与存储。完整事务读取器 `0x40f23658` 未执行：工具用直接批量读取的结果填入构造函数相同的栈位置。这是明确的仿真边界，不能视为执行了事务调度。

复杂控制流程采用摘录执行，栈上的请求由工具显式复制到下一摘录。构造函数的其他字段和后续特殊状态处理未执行，`0x230b` 等未建模状态保持零；这些不是相机现场状态。工具不再将快照结构作为实际采集上下文使用。

本轮仍缺两个决定性环节：取得资源 `0x5c` 的真实参数字节，以解析读出窗口和时序；验证完整事务、区域选择及特殊状态约束，排除本实验省略的字段对实际应用的影响。现有证据支持继续定位这两处，尚不支持制作或刷写全高录像补丁。

后续[更新范围调查](../z8_flash_layout/REPORT.md)已确认，普通 EG 主程序更新的擦写循环不覆盖资源 `0x5c` 所在区间。
