# Z_6_0380.bin 结构与代码分析

分析日期：2026-10-04。对象为`firmware decode/z-series/` 目录的原始样本。

## 主要结论

这份 Z6 C 3.80 更新包能够完整解码。外层格式是 **32 字节待识别前缀 + 旧式三表 XOR 容器**，
并非必须先破解 AES 才能提取程序的情况。解出的四段均通过 CRC-16，整包 CRC 也匹配。
原包重新编码后与输入逐字节一致。

主固件为 ARM 32 位小端代码，混合 ARM 与 Thumb 指令；可采用 Ghidra 的 ARM v7 小端语言开始分析。
有充分的静态证据支持映射基址 `0x10020000`，主程序启动地址为 `0x1002BC88`。
系统含 `SMP T-Kernel Version 1.00.01` 标识。尚未识别具体 SoC 型号，也未完成刷写认证流程逆向。

这纠正了背景材料中的一个关键推断：**没有公开补丁支持，不等于更新包无法解码**。
解包成功同样不能证明只修正 CRC 就能刷入修改版。

## 容器布局与解码

原文件的 `0x00–0x1F` 为待识别前缀：

```text
e923255226716973dac53401c67d173dba1886ddd5a56e931663ed3325aee20b
```

原文件 `0x20–0x3F` 为 32 个 `0x20` 空格字节，这是定位容器原点的标识。
令 `i = 原文件偏移 - 0x20`，从容器偏移 `0x20` 起解码：

```text
plain[i] = input[0x20+i]
         XOR table1[i & 0xff]
         XOR table2[(i >> 8) & 0xff]
         XOR table3[(i >> 16) & 0xff]
```

密钥流的索引周期为 `2^24` 字节，即 16 MiB。它是重复使用的 XOR 混淆，不能作为密码学意义上的一次性密码本。
三张表沿用 [Package.cs](https://github.com/simeonpilgrim/nikon-firmware-tools/blob/main/Nikon-Patch/LocalUI/Package.cs)，
第三张表中的 `0x100` 按原 C# 强转行为截断成 `0x00`。
上游 [LocalUI 的解码入口](https://github.com/simeonpilgrim/nikon-firmware-tools/blob/main/Nikon-Patch/LocalUI/Form1.cs)
本来就检测偏移 0 和 `0x20` 处的空格头；因此不应把这里的 32 字节偏移描述为新破解。

本项目保留容器开头 32 个空格。上游 `Package.LoadData` 对这段也做 XOR，会得到无意义的头部字节；
分段内容不受影响，但核验本样本整包 CRC 时应使用空格头。

目录采用大端整数，与主固件指令的小端字节序不同：

| 容器内偏移 | 内容 |
| --- | --- |
| `0x00–0x1F` | 32 字节空格标识 |
| `0x20` | 分段数 `4`，u32 大端 |
| `0x24` | 头部长度 `0xB0`，u32 大端 |
| `0x28–0x2F` | 两个保留 u32，本样本均为零 |
| `0x30–0xAF` | 4 条目录，每条 32 字节 |
| 每条 `+0x00` | 16 字节文件名字段 |
| 每条 `+0x10` | 分段起点，相对容器原点 |
| 每条 `+0x14` | 分段长度，含两字节 CRC |
| 每条 `+0x18` | 两个保留 u32，本样本均为零 |

## 主固件映射与启动证据

主固件 `eg1620_038000.bi` 首条指令为：

```text
文件偏移 0x00000000: 20 2f 00 ea    b  文件偏移 0x0000BC88
```

`0xBC88` 开始连续清零通用寄存器，随后配置 CP15、MMU/cache、VBAR 和不同异常模式的栈。
它读取 MPIDR 并区分启动核与其他核；这些指令与 SMP 内核字符串相互支持。

基址的验证链为：

1. 启动代码 `0xBD20` 从字面量池 `0xBFD4` 读取 `0x10034140`，下一条写入 VBAR。
2. 文件偏移 `0x14140` 实际存在 ARM 异常向量表，所以基址为 `0x10034140 - 0x14140 = 0x10020000`。
3. 该向量表的复位项从文件偏移 `0x14160` 读取 `0x1002BC88`，恰好等于上述基址加启动偏移。
4. `FirmwareManagement.c` 的若干绝对地址引用也与此基址相符。

这不是简单套用旧机型经验。尤其不能从本样本偏移 `0x20` 读复位地址，因为这里是版本文本。
Pilgrim 的 [D3300 入门教程](https://simeonpilgrim.com/blog/2021/08/07/getting-started-disassembling-nikon-firmware/)
可借鉴工作流程，其具体头部指令布局不能直接照搬。

启动代码中确认了两段复制：

| ROM 源地址 | 主分段文件偏移 | RAM 目的地址 | 长度 |
| --- | --- | --- | --- |
| `0x11E94DD4` | `0x01E74DD4` | `0xC1800000` | `0x00101400` |
| `0x11F96200` | `0x01F76200` | `0xC2A10000` | `0x00000FF8` |

另有 `0x11F97200 → 0xC2A11000` 的零长度复制模板，不需要创建非空数据块。
复制时源和目的寄存器、循环长度直接可见于 [启动反汇编](code_landmarks.asm)。
内存映射不止这些区间，以上只是已确认的导入起点。

建议的 Ghidra 导入步骤（本次未实际运行 Ghidra）：

1. 以 Raw Binary 导入主分段，选择 `ARM:LE:32:v7`，基址 `0x10020000`。
2. 指令分析范围先排除文件末两字节 CRC；在 `0x10020000`、`0x1002BC88`、`0x10034140` 按 ARM 模式反汇编。
3. 将上述两段按文件字节映射到 RAM；主文件映射先作为只读内容，避免把 ROM 指针误认为可变数据。
4. 其他函数按控制流切换 Thumb 模式，不能把整个文件强制按一种指令模式分析。
5. 对照候选函数地址和源码名字符串添加人工标签，再逐步进行自动分析。

## 其他分段

`ex1620_037000.bi` 的首字为初始 SP `0x20000C08`，次字为 Thumb 复位向量 `0x080001C5`。
在基址 `0x08000000`、文件偏移 `0x1C4` 可反汇编出连贯的 M-profile Thumb 启动代码，
它把 `[0x08000000, 0x080001C4)` 复制到 `0x20000000`，再访问 VTOR 地址 `0xE000ED08`。
文件偏移 `0x3709` 有 `Z 6 Firmware Ex Copyright Nikon Corp.`。
因此将其归类为独立 MCU 固件有较强证据；具体芯片及其对焦/测光职责未确认。
EX 内部版本名仍为 03.70.00，不与整个更新包的 C 3.80 矛盾，子固件版本可以不同。

`vr1620_010200.bi` 在偏移 `0x0A` 有 `NikonBVR`，且含大量填充。
结合文件名，推测为机身防抖相关固件；尚未通过代码或硬件对应验证。
`_tpj01_v140.bin` 的用途和指令集本次未确定，不能仅由 `tp` 命名确认是触控固件。

## 可继续追踪的功能入口

以下偏移均相对主分段，不是原始更新包；普通映射地址为偏移加 `0x10020000`。

| 分段偏移 | 内容/线索 | 当前可支持的结论 |
| --- | --- | --- |
| `0x00032F45` | `SMP T-Kernel Version 1.00.01` | 内核身份线索，与 SMP 启动代码一致 |
| `0x00197498`、`0x0019A228` | `FirmwareManagement.c` | 固件管理模块定位入口 |
| `0x001A2E54`、`0x001A3CDC` | `FirmwareChkLib.c` | 校验模块定位入口 |
| `0x001D5BF0` | `FirmwareManagementService.c` | 上层固件管理服务入口 |
| `0x0023EE64` | `MovieRecordApplicationService.c` | 视频录制模块入口 |
| `0x0031021C` | `PtpMemoryControl.c` | PTP 内存控制模块线索；不证明 USB 端可任意读写 |
| `0x0050F130` | `A:\HDMIRAW.KEY` | 与 HDMI RAW 相关的文件路径线索；不等于已找到激活方法 |
| `0x01BABB6C` | `Booted ARM926 Firmware...` | 存在 ARM926 相关子系统；不能将整个主映像归为 ARM926 |

在 `0x101C3BBA` 的 Thumb 函数中，能看到构造 SHA-1 初始状态、调用摘要处理、最终比较 20 字节的行为，
附近还有 `0x5A827999` 常量以及 SHA-1 的旋转/轮运算模式。
将这一局部路径判断为 SHA-1 校验具有较强依据，但它校验的对象、输入格式及其与最外层 32 字节前缀的关系仍需追踪调用者。
这既不能证明有 RSA/ECDSA 签名，也不能证明没有额外认证。

`0x1052F156` 附近另有一段候选文件处理路径，包含读取长度 `0x30` 等操作；
其位置接近 HDMI RAW 文件路径，已保存反汇编以便继续追踪，尚未恢复完整调用关系。
本次在主分段中未找到 ASCII 子串 `LvRaw`；这不能排除不同命名或非 ASCII 表示的功能。

## 已验证与待验证

已验证：输入指纹、所有分段边界、四个分段 CRC、整包 CRC、完整重新编码逐字节一致、
主固件基址/复位/异常向量的一致性，以及测试夹具上的损坏 CRC、截断目录、不安全文件名拒绝和 16 MiB 索引回绕。

尚未验证：最外层 32 字节的含义、完整更新认证链、具体芯片型号、TPJ/VR 指令集、
视频时间限制/码率所在函数、HDMI RAW 激活机制，以及任何修改版本能否被机身接受。
CRC 是差错检测，不提供真实性保证。

下一步最有价值的是追踪 `FirmwareManagement` 到 `FirmwareChkLib` 的调用链，明确包头前缀、摘要和机型/版本检查；
或者以另一份 Z6 官方版本解包后进行分段差异比较，缩小视频与功能管理代码的搜索范围。
这份样本已能提取主程序，因此获取机身 dump 是后续研究运行状态/缺失引导程序的可选方向，不是当前解包的前置条件。

背景材料提到的 2026 年 Rust 解码器链接本次未能访问或独立核实，未作为以上结论依据。
本报告不据此判断整个 Nikon Hacker 社区的当前活跃状态。
